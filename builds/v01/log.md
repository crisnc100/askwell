# Ledgerline v0.1 — build log

Deliberate choices made while building, and why. Newest at the bottom of each phase.

## P1 — Foundations, gold, pre-registration

### P1.1 Scaffold
- **Build backend: `uv_build`** (not hatchling). A backend is needed so `[project.scripts]` installs the `ledgerline` command; uv is already the fixed toolchain, so this adds no new tool.
- **No `types-pyyaml`.** Pyright bundles typeshed's third-party stubs, so a stub package would be an extra dependency outside the fixed stack for no gain.
- **Pyright:** `standard` mode for the repo, `strict` for `ledgerline/core/` (empty until P2). **Ruff rules:** E, F, W, I, B, UP, SIM, RUF, S (bandit), PT, N, C4; S101 (assert) ignored repo-wide; S105/S106/S608 ignored in tests only; S311 (non-crypto random) ignored in the seeder and the Spider selector, where seeded determinism is the point.
- **Zero skips:** `tests/plugins/zero_skips.py` turns any skipped or xfailed test, including collection-time skips such as `importorskip`, into a failed run. It is loaded from `tests/conftest.py`, so plain `uv run pytest` enforces it too, not just `verify.sh`. `tests/test_zero_skips.py` proves it with pytester.
- **detect-secrets:** `verify.sh` runs `detect-secrets-hook --baseline .secrets.baseline` over every tracked and untracked-not-ignored file. The only baseline entries are the local compose/CI dev DB credentials (in `.env.example`, `ledgerline/config.py` defaults and the CI workflow), each marked `is_secret: false`. Inline `pragma: allowlist` comments were tried and dropped: they push lines over ruff's limit and the `nextline` form was not honoured by this detect-secrets version, so the audited baseline is the record.
- **Host port 56432 for compose Postgres** (bound to 127.0.0.1, overridable with `LEDGERLINE_DB_PORT`): a local Postgres already holds 5432 and another project's container holds 55432 on this Mac, and a clash would silently connect tests to the wrong server.
- **`verify.sh` does not yet run `docker compose build`, coverage or the replay eval** (L1): there is no image to build until the P5 Dockerfile, no core module until P2 and no replay report until P4. Each phase adds its step.

### P1.2 Compose and seed
- **Roles:** `infra/postgres/roles.sql` is the one role script; compose runs it at volume init (`infra/postgres/init/10-roles.sh`) and CI runs it with `psql`. `ledgerline_ro` gets CONNECT, USAGE and SELECT (including default privileges for future owner tables), `default_transaction_read_only = on`, and no CREATE. A test proves writes and CREATE fail on privileges even with the read-only default switched off.
- **One seed path:** `uv run ledgerline seed`. The compose `seed` service runs exactly that command in the official uv image (repo mounted read-only, venv outside the mount) and runs on `docker compose up`; `docker compose up -d db` starts Postgres alone. No Dockerfile yet; the api image is P5.
- **Seed is drop-and-recreate** and deterministic: `random.Random(20260630)` plus `Faker.seed_instance`, no wall clock, everything relative to `LEDGERLINE_NOW`. The command prints a content SHA-256; the host (macOS) run and the container (Linux) run printed the same hash (`c2aa7b93…df5ce`).
- **Data shape:** 400 customers, 570 sites, 40 technicians, 120 parts, 5,000 work orders over 2024-06-30 → 2026-06-30 (volume grows about 40%), 7,252 part lines, 4,957 invoices (about 8% of invoiced orders get a supplemental invoice, so `work_orders → invoices` really fans out), 25 users with synthetic `email` and `password_hash` (random bytes in a pbkdf2-shaped string, not a hash of any password).
- **Timestamps are naive UTC** in both engines, so SQLite fixtures and Postgres hold identical values; the tests compare the Postgres content hash with a freshly generated SQLite load.
- **Tests never seed Postgres themselves.** The `pg_seeded` fixture fails (never skips) with the exact commands to run when Postgres is unreachable or holds different data, so a test run cannot silently rewrite a dev DB.

### P1.3 Model gateway (`ledgerline/llm/`)
- **Transport seam.** `Gateway` owns modes, replay, cost, budget and backoff; `OpenRouterTransport` is the only code that talks to OpenRouter (LangChain `ChatOpenAI`, `with_structured_output(method="json_schema", include_raw=True)`). Tests drive the gateway with a fake transport and drive the real transport through `httpx.MockTransport`, so no test touches the network.
- **Provider pinning:** every request sends `provider.require_parameters = true`, so OpenRouter routes only to upstream providers that support `response_format`; an explicit provider `order` (with fallbacks off) is optional, to be filled from the spike. `strict` json_schema is off by default because Pydantic's schemas mark optional fields as not-required, which OpenAI-style strict mode rejects; the spike decides whether to turn it on.
- **`max_tokens` is sent in the body** under OpenRouter's documented name. `ChatOpenAI` would otherwise send `max_completion_tokens`, which OpenRouter's docs do not list (*unverified* whether it is honoured, so it is avoided). A test asserts the body.
- **Parse path:** the provider's parse is validated with Pydantic; with no parse, the text (code fences stripped) is validated with Pydantic; anything else is a typed `ParseError` carrying the raw text. A recorded response is stored before parsing, so replay reproduces a `ParseError` too.
- **Replay key** = SHA-256 of canonical JSON of (model, prompt_version, messages, JSON schema). **Agent trajectories** use a separate store keyed `system|question_id|model|prompt_version` (separator rejected inside parts). Both stores are append-only JSONL, last write wins. A miss raises `ReplayMissError` and never falls back to live (tested with a transport that would answer).
- **Cost:** `usage.cost` from OpenRouter when present (requested with `usage.include = true`; the mocked-HTTP test proves the field survives LangChain's response handling), else estimated from the models-endpoint pricing; neither is an error. Replay reports the recorded cost with `cost_source = "replay"` and charges nothing.
- **Worst-case pre-check:** prompt characters (messages + schema, as canonical JSON) × prompt price + `max_tokens` × completion price. A token is at least one character, so this is a true upper bound. An unknown price refuses the call: no pre-check, no call.
- **Budget across a run:** `run_checkpointed` appends one fsynced JSONL line per finished item, skips finished items on resume, and starts the guard at the checkpoint's total spend, so `--budget` is the run's total, not per invocation. Spend from an item that stopped midway (budget stop or crash) is written as a spend-only line so a resume cannot re-spend it. A torn last line from a killed run is ignored. The outcome carries `aborted`, `abort_reason` and `is_partial`, which the P4 report will render as a partial report.
- **429 backoff:** only HTTP 429 is retried (5 retries, exponential from 1 s, capped at 30 s), detected by `status_code` on the exception or its response; `ChatOpenAI`'s own retries are off so they don't multiply. Other errors propagate at once.

### P1.4 Model spike — command built, live run PENDING
- **`ledgerline spike --models a,b,… --budget 0.50`** runs five fixed probes per candidate through the real gateway in live mode (temperature 0, one shared hard budget across all candidates) and writes `evals/spike/spike-<UTC stamp>.json`. Outcomes per probe: `honoured` (the provider returned a parse that validates), `text_fallback` (only the Pydantic text fallback validated), `parse_error`, `error`; plus exact-match against the expected extraction, cost and latency. It also records whether OpenRouter's models endpoint advertises `structured_outputs` for each model.
- **The probe schema is a generic support-ticket extraction,** not Ledgerline's intent: the spike measures json_schema support and must not leak intent design ahead of the frozen gold set.
- **Not run: `OPENROUTER_API_KEY` is not set in this environment.** No result, model choice or cost is recorded anywhere; ADR-004 says PENDING. The command refuses with exit code 2 without a key (tested).
- Read-only context for whoever runs it (public `GET /models`, no key, 2026-11-09): non-batch models advertising `structured_outputs` under $0.50/M prompt include `openai/gpt-oss-20b`, `openai/gpt-oss-120b`, `deepseek/deepseek-v4-flash-0731`, `mistralai/mistral-small-24b-instruct-2501`, `google/gemma-3-12b-it`, `meta-llama/llama-3.1-8b-instruct`. Advertised support is not proof; that is what the spike measures.

### P1.5 Gold set
- **67 items:** 43 in_schema (16 easy, 15 medium, 12 hard), 13 out_of_schema, 11 should_refuse. All six features appear. Written from the fieldservice schema and the category definitions, as manager questions, before any intent code; about a quarter of the in_schema items need constructs a simple grammar may not have (correlated subqueries, `NOT EXISTS`, `FILTER` ratios, `generate_series`, interval arithmetic). That is deliberate: misses there are coverage findings.
- **Refusal difficulty:** refusal items are mostly `easy`; the ones next to real tables or mixing visible and hidden fields (parts stock, technician certifications, profit after payroll, username + email, "login credentials", export emails and hashes) are `medium`.
- **Interpretation conventions** (relative periods as literals against `LEDGERLINE_NOW`, void exclusion, attribution paths, unique tiebreakers on every ORDER BY) are written down in `evals/gold/README.md` so the gold is auditable.
- **Gold test** runs each in_schema `gold_sql` twice on the seeded Postgres as the read-only role and compares (as a sequence when `ordered`, else as a sorted multiset). Beyond the plan's non-empty rule it also fails a result whose every value is NULL (a `sum` over no rows returns one NULL row and would otherwise count as non-empty).
- **Item schema lives in `ledgerline/gold.py`** (Pydantic, `extra="forbid"`) so P4's eval loads the same model the test validates; it enforces the category shape (in_schema has SQL and no refusal reason; refusals have null SQL, a reason, no features; `ordered` needs an ORDER BY).
- The JSONL was produced once from a scratch script outside the repo; from now on the JSONL is the source and any change goes through `CHANGELOG.md`.

### P1.7 Gold manifest
- **`evals/gold/MANIFEST.json`** holds SHA-256 of `fieldservice.jsonl`, `spider_ids.json` and `spider_selection.py` (the selection rule is gold too: editing the seed or the rule must be visible) plus a `revision` number.

## P2 — Registry, validator, SQL builder, executor

Decisions from the P1 checkpoint (team lead, 2026-11-09): the grammar grows by exactly two things, a 3-hop path limit (was 2) and column-to-column comparison filters; computed expressions, anti-joins, multi-date series and DISTINCT-in-HAVING stay out (they remain `grammar_gap` misses). The gold set is untouched. The read-only role is denied `users.email` and `users.password_hash` at the database level.

### Defence in depth: column-level REVOKE
- `ledgerline seed` revokes the table-level grant on `users` from `ledgerline_ro` and grants SELECT on a column list without `email` and `password_hash` (`RO_DENIED_COLUMNS` in `fieldservice/schema.py`). A table-level grant would cover every column, so a column REVOKE alone does nothing. Proven by a test: as `ledgerline_ro`, `SELECT password_hash FROM users`, `SELECT email …` and `SELECT * FROM users` all fail with "permission denied"; `SELECT username, role` works. The registry still hides both fields; this is the layer that holds if the registry or the validator is ever wrong.
- Consequence: the read-only role can no longer read every column, so the `pg_seeded` fixture now reads the content hash as the owner (assertion unchanged). That test-only change is its own commit (`ecdaf95`) with the reason in its message.
- **App DB:** `roles.sql` creates `ledgerline_app` (owner-only; `ledgerline_ro` has no CONNECT, tested) for the `ask_log` audit table, so the analyst role can never read the audit trail and the data DB stays free of Ledgerline's own tables. `LEDGERLINE_APP_DATABASE_URL` is new config. An existing local volume needs `roles.sql` re-run (idempotent) or `docker compose down -v`.

### Registry (`core/registry.py`)
- Entities and fields are keyed by registry-safe slugs (`^[a-z][a-z0-9_]*$`) and carry the real identifier (`table`, `column`), so spaces, dots, quotes and case never reach SQL text unquoted (tested with `"Order Lines"."Unit.Price"`, a column named `select`, and one named `a"b`).
- `aggregatable` governs sum/avg/min/max only; count and count_distinct work on any visible field (counting ids is normal; summing them is not). Categorical value matching is case-insensitive and resolves `value_aliases` (e.g. "Texas" → "TX", "done" → "completed").
- The model enforces its own invariants (allowed_values only on categoricals, hidden fields never categorical, value aliases point at allowed values, keys and relationships reference real fields, no unknown keys, so no SQL can be smuggled into the YAML).

### Intent and validator (`core/intent.py`, `core/validate.py`)
- Filters are a top-level AND of conditions and one-level `any_of` / `all_of` groups (groups never nest). A condition has exactly one operand form: `value`, `values` (in; between as [low, high]) or `other_field` (the new column comparison, eq..lte only).
- Every plan rule has a named test `test_rule_<code>`, and a meta-test fails if any error code lacks one. Plan rule → code: unknown entity/field → `unknown_entity`/`unknown_field`; hidden → `hidden_field`; not filterable/aggregatable → `not_filterable`/`not_aggregatable`; aggregate vs type → `aggregate_type`; operator vs type → `operator_type`; value vs field type → `value_type`; allowed values → `value_not_allowed`; limit → `limit_out_of_range`; empty in → `empty_in`; reversed between → `reversed_between`; date_range on non-date → `date_range_field_type`; date_range duplicating a filter → `date_range_duplicate`; intent_type vs fields → `intent_shape`; having without group_by → `having_without_group_by`; unreachable → `unreachable_field`; ambiguous → `ambiguous_path`; fan-out → `fan_out`; draft → `draft_registry`. Codes the plan's rules needed in practice: `value_shape` (wrong operand form), `invalid_date_range`, `grain_type`, `unknown_metric`, `invalid_alias`, `duplicate_alias`, `invalid_order_by`, `column_comparison_type` (new grammar), and `one_to_many_join` (below).
- **Paths:** breadth-first search over the relationship graph in both directions, counting shortest paths, up to 3 hops. More than one shortest path is `ambiguous_path` (never a silent pick). Self-references are ignored (no self-joins). If the unique shortest path crosses a one-to-many edge, it is `fan_out` when the intent aggregates and `one_to_many_join` for a row list: the builder joins many-to-one only, so a row list along a one-to-many edge would silently multiply rows. Both are tested at 1 and 3 hops; ambiguity is tested at 1 and 3 hops.
- **Column comparisons** compare type families (integer/number, date/datetime, text, boolean); both sides go through the same resolution, hidden, filterable and fan-out checks (tested: `completed_at < invoices.issued_at` from work_orders is `fan_out`).
- **Dates:** relative tokens resolve in code to half-open [start, end) against `LEDGERLINE_NOW`; "this_*"/ytd end at the reference time. The token table is tested against the gold conventions (last 90 days = 2026-04-01, last 6 months = 2025-12-30, last quarter = 2026-Q1). On a DATE column bounds are dates, and a mid-day end includes that day.
- The validator never raises for a bad intent; it collects every issue with a location and returns a `QueryPlan` only when there are none.

### SQL builder (`core/sqlbuild.py`)
- SQLAlchemy Core with lightweight `table()`/`column()` built only from plan identifiers; every value is a bound parameter. The Hypothesis property (300 examples, Postgres and SQLite) uses sentinel values: text sentinels carry SQL metacharacters (quotes, `;`, `--`, `%`, `_`, `\`, unicode) and numeric sentinels are large odd values (7,000,000,001+, or ~1e9 + .123), so they cannot collide with `LIMIT 1` or labels. That is the sentinel design, not a narrowed generator. It asserts no sentinel appears in SQL text and each is in the bound params (`ilike_contains` binds with LIKE wildcards escaped, which the check unescapes).
- **Joins are INNER** along many-to-one edges. A base row whose foreign key is NULL drops out only when a field across that edge is used, which matches how the gold questions are written (e.g. counts by technician skill level).
- **Grains** return the first day of the period as a DATE on both engines: Postgres `CAST(date_trunc(unit, x) AS DATE)` (`week` is ISO, Monday start); SQLite date modifiers (`'weekday 0', '-6 days'` for the ISO Monday; a computed month offset for the quarter). Other dialects raise a CompileError. Cross-dialect tests cover 11 edge dates (ISO weeks across year ends, quarter ends, a leap day) as DATE and as 23:59:59 DATETIME, all grains, both engines, against a Python reference.
- **Numbers come back as float** (`Numeric(asdecimal=False)`) on both engines, so results compare across engines and SQLite emits no Decimal warnings.

### Executor and audit (`core/executor.py`, `core/audit.py`)
- Postgres: `readonly_engine` sets every new session to read-only, and every `run` starts `SET TRANSACTION READ ONLY` and `SET LOCAL statement_timeout`, then rolls back. Tested: even an owner URL through `readonly_engine` cannot write. SQLite: `file:…?mode=ro` plus `PRAGMA query_only`, and a progress handler interrupts past the deadline. Tested on both engines: INSERT, UPDATE, DELETE, DROP and CREATE fail and the content hash is unchanged; `pg_sleep(5)` and an infinite recursive CTE are cancelled at 0.2–0.3 s and the connection is reusable; the row cap fetches cap+1 to flag truncation.
- `ask_log` stores trace id, schema id, question, intent JSON, validation JSON, SQL with placeholders, a SHA-256 of the params, row count, cost, model and outcome (answered/refused/error). Never rows and never raw params (tested: no result value appears anywhere in the stored row). Failed executions are logged as `error`.

### `registry init` (`core/registry_init.py`, `ledgerline registry init`)
- Opens the database read-only. Reads no data unless `--values`; with it, a text field becomes categorical when it has 1–50 distinct values, is not hidden, is not name-like (`name|title|desc|comment|note|address|street|url`), and is not one-value-per-row in a table of more than 5 rows (an identifier, e.g. `sku`).
- Declared single-column foreign keys to a single-column primary key become `declared`; others are skipped with a warning (composite, unknown table, or non-PK target such as Spider `car_1`'s `car_names.Model`). Without a declared key, `<x>_id` pointing at table `x`, `xs` or `xes`, or a column named exactly like another table's primary key (other than `id`), becomes `inferred`; several candidates infer nothing and warn.
- Key columns (PK, FK, `*_id`) are not aggregatable; numeric and date measures are. Sensitive names (`password|hash|token|secret|ssn|email|phone`) are hidden and not filterable.
- Write-privilege warning: Postgres checks `has_table_privilege(INSERT, UPDATE, DELETE, TRUNCATE)` per table (the owner warns, `ledgerline_ro` does not); SQLite warns when the file is writable by the user.
- Determinism: same DB in, byte-identical YAML out (tested twice per DB), and Postgres and SQLite introspection of fieldservice produce equal registries.
- **Every sampled Spider DB** (dog_kennels, car_1, flight_2, wta_1, network_1) is initialised twice and loads, in the test suite. CI now caches and fetches the checksum-pinned archive before the tests; without the data the test fails with the fetch command, never skips.

### Fieldservice registry (`registries/fieldservice.yaml`)
- Drafted with `registry init --values`, then curated: descriptions, entity and field aliases, value aliases, `draft: false`. A test fails if curation changed anything structural (identifiers, types, flags, allowed values, relationships) relative to fresh introspection.

### Coverage gate
- `verify.sh` runs pytest with `--cov-branch` and then `scripts/check_coverage.py`, which fails if a listed module is below its **branch** floor or is missing from the report: validate.py and sqlbuild.py ≥ 95%, executor.py and registry_init.py ≥ 85%.

### Oracle check
- The 30 oracle intents each have a reference query written by hand from the question, run on Postgres; the builder's rows on Postgres and on SQLite must match it. To check that the oracle can fail, two bugs were planted temporarily (ISO week off by a day in SQLite; `is_null` inverted). It failed 3 cases, and the file was restored.

### PR1 grade fix round (astra, `builds/v01/grade-pr1.json`)
Each fix's test was committed first, in a test-only commit, and failed before the fix: 14 failing tests, all on SQLite for the temporal case. Postgres already compared correctly.
- **L4, booleans inlined.** `customers.is_active eq true` compiled to `= true` / `= 1` with no params, because bare Python booleans become SQL literals in SQLAlchemy. Every filter and HAVING value now goes through `bindparam(None, value, type_=<column type>)`, including each element of IN and both bounds of BETWEEN, so the column's type processor binds it on each engine. The sentinel property was strengthened, not narrowed. It now also generates boolean, datetime and integer-IN filters, and asserts the bound-parameter count equals the number of filter values, so an inlined literal of any type fails. A boolean must be bound as that exact boolean (True == 1 in Python).
- **L11b, torn checkpoint tail.** Load used to stop at the torn line, but appends landed after it, so later records were never read again. Now `load` cuts a torn final line off the file (or adds the missing newline if the line is complete), and skips rather than stops at any other bad line. `append` starts on a fresh line if the file does not end in a newline, so a record is never glued onto a fragment.
- **f-alias.** A metric alias equal to a group label shadowed the group in ORDER BY. The new code `alias_collision` covers an explicit metric alias that reuses a group label, and the same field grouped twice. Default metric labels step around group labels (`count_2`). Group-by is now validated before metrics so the labels are known. The builder also raises on any duplicate output label as a second guard.
- **f-temporal.** Comparing a DATE column with a DATETIME column now normalises both sides to a datetime: `CAST(x AS TIMESTAMP)` on Postgres, `strftime('%Y-%m-%d %H:%M:%f', x)` on SQLite. The SQLite form reads any stored date or datetime text format, so midnight on the same day compares equal. Caveat: SQLite normalisation is to millisecond precision, so a sub-millisecond difference against a date's midnight compares equal on SQLite only. Same-type comparisons are left as they were.
- **f-roles.** `roles.sql` re-applies the users column restriction after its table-wide `GRANT SELECT ON ALL TABLES`, building the column list from `information_schema`. It is skipped while `users` does not exist; compose init runs before the seed. A test keeps its denied list equal to `RO_DENIED_COLUMNS`. A test also runs `roles.sql` twice with `psql` on the seeded DB, and `ledgerline_ro` still gets "permission denied" on `password_hash` and `email`. This bug was observed for real during the fix round: running the new test before the fix left the dev DB with table-wide SELECT on users, and `test_hidden_columns_are_denied_by_the_database_too` caught it.
- **L8:** no change. The grader's sandbox could not reach Postgres.

## PR2 — deferred items from the PR1 close (branch `pipeline`)
- **c3, worst-case prompt cost** (`72bf682`): the pre-check bounds prompt tokens by UTF-8 bytes, not characters. Byte-level tokenizers never emit a token shorter than a byte, while one CJK character is 3 bytes. Test: `test_precheck_bounds_unicode_prompts_by_utf8_bytes`. ADR-005's prediction text still says "prompt characters"; predictions are not edited after the fact, so the measured result will note the change.
- **r1/x2, HAVING thresholds** (`f3c2942`): bound as NUMERIC instead of the aggregate's type, so `count > 1.5` is no longer cast to `> 2` on Postgres. Filter BETWEEN bounds keep their column type, because the validator only admits integers for integer fields. Test: `test_fractional_having_thresholds_are_not_rounded`, on both engines.
- **r2/x3, microseconds** (`2d84fb2`): SQLite's DATE-vs-DATETIME normalisation builds `'YYYY-MM-DD HH:MM:SS' || '.' || <stored fraction padded to 6>`, so `00:00:00.000001` is greater than its DATE on both engines. Test: `test_date_vs_datetime_keeps_microseconds`. Unsupported on SQLite: a fraction followed by a UTC offset, which SQLAlchemy never writes.

## P3 — Pipeline, API, CLI (in progress)
- **Simulation path** (plan.md, Decision 2026-11-09). The gateway has a new `export` mode. A recorded key replays as usual; an unrecorded key is written to `evals/pending/<key>.json` and raises `PendingRequestError`. That file holds the target model, prompt version, system prompt, full messages, response schema, context and answer instructions. `ledgerline replay import` loads `<key>.answer.json` files into `evals/recordings/interpret.jsonl` with cost 0 and provenance `{"simulated_by", "standing_in_for"}`. Every replayed result carries that provenance. A `response_text` answer (not a JSON object) is imported as raw text and replays as a `ParseError`, the same as a real model's bad output would. Import never invents an answer, and unanswered requests stay pending. `evals/pending/` is gitignored.
- **Provisional target model** `openai/gpt-oss-120b`, set as the `LEDGERLINE_DEFAULT_MODEL` default. The real spike (ADR-004) is deferred, and it is part of every replay key. Picked from the P1 list of cheap models that advertise `structured_outputs`; open for the orchestrator to confirm.
- **Graph** (`pipeline/graph.py`, LangGraph): interpret → validate → retry (once, with the typed issues or the parse error fed back as a user turn after the model's own answer) → execute → present. `present` is deterministic and rows never go to the model (tested). Outcomes: unanswerable gives a refusal with the model's reason; a second failed attempt gives a refusal naming the codes; an execution failure gives a refusal with the error. Every attempt (answer, intent, issues) is returned in `validation.attempts` for the trace view.
- **Prompt** (`interpret-v1`): fixed instructions plus a registry view in registry order. Hidden fields are never listed. The reference date is shown, and the model is told to use relative tokens and never compute dates. Truncation is deterministic, at 16,000 characters by default: allowed values past 20 per field go first, then descriptions are cut to 60 characters, then removed. Each step is logged and returned in `prompt_truncation`.
- **Audit:** answered and failed executions are written by the executor; refusals by the service. Each ask is one `ask_log` row.
- **API:**
  - `POST /ask` returns `{intent, validation, sql, params, rows, columns, refusal, trace_id, cost_usd}`, plus `truncated`, `model`, `provenance` and `prompt_truncation`.
  - `GET /schemas`, `GET /schemas/{id}/examples`, `GET /healthz`.
  - An unrecorded question in replay mode returns 409 with a pointer to the canned examples. A pending export also returns 409.
  - **CLI:** `ledgerline ask` and `ledgerline replay import`.
- **Test doubles vs recordings:** retry-then-success, parse errors and two-failure refusals use a scripted test-double gateway (`tests/pipeline/conftest.py::ScriptedGateway`), because a recording cannot honestly force a first answer to be wrong. It is never written to the replay store. The replay API tests (answerable, hidden-field, out-of-registry and write refusals, init → ask on Spider `dog_kennels`) use only imported simulated answers.
- **Replay cases** (`evals/replay_cases.py export`): the 7 canned fieldservice examples (written for the demo, distinct from the gold questions) and one Spider question written for this test (not Spider text), on an unedited `registry init --values` of dog_kennels. First export: 8 pending requests.
