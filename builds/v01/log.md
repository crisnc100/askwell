# Ledgerline v0.1 — build log

Deliberate choices made while building, and why. Newest at the bottom of each phase.

## P1 — Foundations, gold, pre-registration

### P1.1 Scaffold
- **Build backend: `uv_build`** (not hatchling). A backend is needed so `[project.scripts]` installs the `ledgerline` command; uv is already the fixed toolchain, so this adds no new tool.
- **No `types-pyyaml`.** Pyright bundles typeshed's third-party stubs, so a stub package would be an extra dependency outside the fixed stack for no gain.
- **Pyright:** `standard` mode for the repo, `strict` for `ledgerline/core/` (empty until P2). **Ruff rules:** E, F, W, I, B, UP, SIM, RUF, S (bandit), PT, N, C4; S101 (assert) ignored repo-wide; S105/S106/S608 ignored in tests only; S311 (non-crypto random) ignored in the seeder and the Spider selector, where seeded determinism is the point.
- **Zero skips:** `tests/plugins/zero_skips.py` turns any skipped or xfailed test, including collection-time skips such as `importorskip`, into a failed run. It is loaded from `tests/conftest.py`, so plain `uv run pytest` enforces it too, not just `verify.sh`. `tests/test_zero_skips.py` proves it with pytester.
- **detect-secrets:** `verify.sh` runs `detect-secrets-hook --baseline .secrets.baseline` over every tracked and untracked-not-ignored file. The only baseline entries are the local compose/CI dev DB credentials (in `.env.example`, `ledgerline/config.py` defaults and the CI workflow), each marked `is_secret: false`. Inline `pragma: allowlist` comments were tried and dropped: they push lines over ruff's limit and the `nextline` form was not honoured by this detect-secrets version, so the audited baseline is the record.
- **Host port 56432 for compose Postgres** (bound to 127.0.0.1, overridable with `LEDGERLINE_DB_PORT`): a local Postgres already holds 5432 and another project's container holds 55432 on this Mac, and a clash would silently connect tests to the wrong server.
- **`verify.sh` does not yet run `docker compose build`, coverage or the replay eval** (L1): there is no image to build until the P5 Dockerfile, no core module until P2 and no replay report until P4. Each phase adds its step.

### P1.2 Compose and seed
- **Roles:** `infra/postgres/roles.sql` is the one role script; compose runs it at volume init (`infra/postgres/init/10-roles.sh`) and CI runs it with `psql`. `ledgerline_ro` gets CONNECT, USAGE and SELECT (including default privileges for future owner tables), `default_transaction_read_only = on`, and no CREATE. A test proves writes and CREATE fail on privileges even with the read-only default switched off.
- **One seed path:** `uv run ledgerline seed`. The compose `seed` service runs exactly that command in the official uv image (repo mounted read-only, venv outside the mount) and runs on `docker compose up`; `docker compose up -d db` starts Postgres alone. No Dockerfile yet; the api image is P5.
- **Seed is drop-and-recreate** and deterministic: `random.Random(20260630)` plus `Faker.seed_instance`, no wall clock, everything relative to `LEDGERLINE_NOW`. The command prints a content SHA-256; the host (macOS) run and the container (Linux) run printed the same hash (`c2aa7b93…df5ce`).
- **Data shape:** 400 customers, 570 sites, 40 technicians, 120 parts, 5,000 work orders over 2024-06-30 → 2026-06-30 (volume grows about 40%), 7,252 part lines, 4,957 invoices (about 8% of invoiced orders get a supplemental invoice, so `work_orders → invoices` really fans out), 25 users with synthetic `email` and `password_hash` (random bytes in a pbkdf2-shaped string, not a hash of any password).
- **Timestamps are naive UTC** in both engines, so SQLite fixtures and Postgres hold identical values; the tests compare the Postgres content hash with a freshly generated SQLite load.
- **Tests never seed Postgres themselves.** The `pg_seeded` fixture fails (never skips) with the exact commands to run when Postgres is unreachable or holds different data, so a test run cannot silently rewrite a dev DB.

### P1.3 Model gateway (`ledgerline/llm/`)
- **Transport seam.** `Gateway` owns modes, replay, cost, budget and backoff; `OpenRouterTransport` is the only code that talks to OpenRouter (LangChain `ChatOpenAI`, `with_structured_output(method="json_schema", include_raw=True)`). Tests drive the gateway with a fake transport and drive the real transport through `httpx.MockTransport`, so no test touches the network.
- **Provider pinning:** every request sends `provider.require_parameters = true`, so OpenRouter routes only to upstream providers that support `response_format`; an explicit provider `order` (with fallbacks off) is optional, to be filled from the spike. `strict` json_schema is off by default because Pydantic's schemas mark optional fields as not-required, which OpenAI-style strict mode rejects; the spike decides whether to turn it on.
- **`max_tokens` is sent in the body** under OpenRouter's documented name. `ChatOpenAI` would otherwise send `max_completion_tokens`, which OpenRouter's docs do not list (*unverified* whether it is honoured, so it is avoided). A test asserts the body.
- **Parse path:** the provider's parse is validated with Pydantic; with no parse, the text (code fences stripped) is validated with Pydantic; anything else is a typed `ParseError` carrying the raw text. A recorded response is stored before parsing, so replay reproduces a `ParseError` too.
- **Replay key** = SHA-256 of canonical JSON of (model, prompt_version, messages, JSON schema). **Agent trajectories** use a separate store keyed `system|question_id|model|prompt_version` (separator rejected inside parts). Both stores are append-only JSONL, last write wins. A miss raises `ReplayMissError` and never falls back to live (tested with a transport that would answer).
- **Cost:** `usage.cost` from OpenRouter when present (requested with `usage.include = true`; the mocked-HTTP test proves the field survives LangChain's response handling), else estimated from the models-endpoint pricing; neither is an error. Replay reports the recorded cost with `cost_source = "replay"` and charges nothing.
- **Worst-case pre-check:** prompt characters (messages + schema, as canonical JSON) × prompt price + `max_tokens` × completion price. A token is at least one character, so this is a true upper bound. An unknown price refuses the call: no pre-check, no call.
- **Budget across a run:** `run_checkpointed` appends one fsynced JSONL line per finished item, skips finished items on resume, and starts the guard at the checkpoint's total spend, so `--budget` is the run's total, not per invocation. Spend from an item that stopped midway (budget stop or crash) is written as a spend-only line so a resume cannot re-spend it. A torn last line from a killed run is ignored. The outcome carries `aborted`, `abort_reason` and `is_partial`, which the P4 report will render as a partial report.
- **429 backoff:** only HTTP 429 is retried (5 retries, exponential from 1 s, capped at 30 s), detected by `status_code` on the exception or its response; `ChatOpenAI`'s own retries are off so they don't multiply. Other errors propagate at once.

### P1.4 Model spike — command built, live run PENDING
- **`ledgerline spike --models a,b,… --budget 0.50`** runs five fixed probes per candidate through the real gateway in live mode (temperature 0, one shared hard budget across all candidates) and writes `evals/spike/spike-<UTC stamp>.json`. Outcomes per probe: `honoured` (the provider returned a parse that validates), `text_fallback` (only the Pydantic text fallback validated), `parse_error`, `error`; plus exact-match against the expected extraction, cost and latency. It also records whether OpenRouter's models endpoint advertises `structured_outputs` for each model.
- **The probe schema is a generic support-ticket extraction,** not Ledgerline's intent: the spike measures json_schema support and must not leak intent design ahead of the frozen gold set.
- **Not run: `OPENROUTER_API_KEY` is not set in this environment.** No result, model choice or cost is recorded anywhere; ADR-004 says PENDING. The command refuses with exit code 2 without a key (tested).
- Read-only context for whoever runs it (public `GET /models`, no key, 2026-11-09): non-batch models advertising `structured_outputs` under $0.50/M prompt include `openai/gpt-oss-20b`, `openai/gpt-oss-120b`, `deepseek/deepseek-v4-flash-0731`, `mistralai/mistral-small-24b-instruct-2501`, `google/gemma-3-12b-it`, `meta-llama/llama-3.1-8b-instruct`. Advertised support is not proof; that is what the spike measures.

### P1.5 Gold set
- **67 items:** 43 in_schema (16 easy, 15 medium, 12 hard), 13 out_of_schema, 11 should_refuse. All six features appear. Written from the fieldservice schema and the category definitions, as manager questions, before any intent code; about a quarter of the in_schema items need constructs a simple grammar may not have (correlated subqueries, `NOT EXISTS`, `FILTER` ratios, `generate_series`, interval arithmetic). That is deliberate: misses there are coverage findings.
- **Refusal difficulty:** refusal items are mostly `easy`; the ones next to real tables or mixing visible and hidden fields (parts stock, technician certifications, profit after payroll, username + email, "login credentials", export emails and hashes) are `medium`.
- **Interpretation conventions** (relative periods as literals against `LEDGERLINE_NOW`, void exclusion, attribution paths, unique tiebreakers on every ORDER BY) are written down in `evals/gold/README.md` so the gold is auditable.
- **Gold test** runs each in_schema `gold_sql` twice on the seeded Postgres as the read-only role and compares (as a sequence when `ordered`, else as a sorted multiset). Beyond the plan's non-empty rule it also fails a result whose every value is NULL (a `sum` over no rows returns one NULL row and would otherwise count as non-empty).
- **Item schema lives in `ledgerline/gold.py`** (Pydantic, `extra="forbid"`) so P4's eval loads the same model the test validates; it enforces the category shape (in_schema has SQL and no refusal reason; refusals have null SQL, a reason, no features; `ordered` needs an ORDER BY).
- The JSONL was produced once from a scratch script outside the repo; from now on the JSONL is the source and any change goes through `CHANGELOG.md`.

### P1.6 Spider pre-registration
- **Source verified, not assumed:** the download URL is the Google Drive file linked from the official page (https://yale-lily.github.io/spider), which also states CC BY-SA 4.0 (licence also confirmed in the Hugging Face card metadata for `xlangai/spider`). The archive is the 2020-08-03 revision (`README.txt` inside). The SHA-256 `00636695…5121b` was computed from the actual download on 2026-11-09 and pinned in `scripts/fetch_benchmarks.py`; a mismatch deletes the file and extracts nothing.
- **Fetch script** (`uv run python -m scripts.fetch_benchmarks`) streams to a `.part` file, verifies, extracts into gitignored `data/spider/` while skipping `__MACOSX`/`.DS_Store` and refusing any path that escapes the target, and writes `LICENSE_NOTICE.txt` with the citation and licence. Tests use an in-memory zip over `httpx.MockTransport`; nothing in the test suite downloads.
- **IDs are 0-based indices into `dev.json`** (Spider dev has no native question ids). `spider_ids.json` also records `dev.json`'s SHA-256 so the indices are tied to one exact file.
- **Hardness is a port of Spider's `eval_hardness`** (taoyds/spider `evaluation.py`, Apache-2.0, same licence as this repo) run on dev.json's pre-parsed `sql`, so no SQL parser dependency is needed. Ported as is, quirks included. Check: it reproduces the published dev split exactly (248 easy / 446 medium / 174 hard / 166 extra), and a test pins that.
- **Selection rule** (in the module docstring and committed with its output): eligible = dev databases with ≥ 50 questions (9 of 20; the eval needs 50 per DB); 5 drawn with `random.Random(20261109).sample` over the sorted eligible list; 50 per DB, proportional to hardness by largest remainder, sampled within strata. Result: `dog_kennels`, `car_1`, `flight_2`, `wta_1`, `network_1`. Nobody looked at which databases Ledgerline could handle; the seed is the date this step ran.
- **Reproduction check:** `uv run python -m evals.gold.spider_selection --check` recomputes from `data/` and compares byte for byte (passes now). It is not in `verify.sh`, because CI has no Spider data and fetching 206 MB from Google Drive on every run would be flaky; the committed file's shape and the algorithm are tested without data.
- **detect-secrets flags SHA-256 checksums** as high-entropy hex. Each one is reviewed and marked `is_secret: false` in the baseline; `scripts/update_secrets_baseline.sh` rescans and lists every finding for review but never marks anything itself.

### P1.7 Gold manifest
- **`evals/gold/MANIFEST.json`** holds SHA-256 of `fieldservice.jsonl`, `spider_ids.json` and `spider_selection.py` (the selection rule is gold too: editing the seed or the rule must be visible) plus a `revision` number.
- **The change rule is enforced, not just documented:** `CHANGELOG.md` entries `## Revision N — YYYY-MM-DD` must run 1..revision with a non-empty reason, so a hash bump without a reason fails the test. `uv run python -m evals.gold.manifest --update --reason "…"` is the one way to change gold (refuses an empty reason); `--check` is the CLI form of the test.
- **`.gitattributes` marks gold files `-text`** so line-ending conversion on another machine cannot change their bytes and break the hashes.
- **MANIFEST.json is excluded from the secret scan:** it holds only file hashes by construction, and every gold revision would otherwise add fresh high-entropy "findings" to audit.
