# Ledgerline v0.1 — context

## Product
A governed AI data analyst. People ask business questions in plain English and get answers backed by an auditable, parameterized SQL query. The LLM never writes SQL: it fills in a typed intent, plain Python validates every field against a registry, and a query builder writes the SQL.

The portfolio claim to prove is that this works on schemas it was not tuned on (a synthetic business schema, public text-to-SQL benchmark databases, and any user's own database via `registry init`), with an honest comparison against LangChain's SQL agent, including where the agent wins.

## Audience
- Technical recruiters and hiring managers for applied-AI roles. They read the README, eval table and ADRs, and watch a 90-second video.
- Developers who clone it and point it at their own database.

## Environment (checked 2026-11-09)
- uv 0.9.11, Python 3.14 is on the machine, but the project pins Python 3.12 via uv for library compatibility.
- Docker 29 with the daemon up. Node 23. pnpm is not installed, so use npm.
- gh is installed but not logged in. Pushing waits on `gh auth login` (Cristian).
- The repo is a fresh git repo at `~/Documents/Projects/ledgerline`. The worktree is `ledgerline-v01` on branch `v01`, and there is no remote yet.

## Constraints
- **LLM access goes through OpenRouter** (OpenAI-compatible API) via LangChain's `ChatOpenAI` with `base_url`. Cheap models by default. The model id comes from config, never hardcoded in logic.
- **Budget:** $50/month total across both projects' betas. Every live run has a hard per-run budget, and CI never calls a live model.
- **Replay mode:** recorded model responses let tests, CI and demos run with no API key.
- **The repo is public from day one.** Never commit secrets, and keep `.env.example` only.
- **Spider and BIRD data are CC BY-SA** (verify the licences when writing the fetch script). Do not commit them. Fetch them by script.

## Out of scope for v0.1
Documents RAG and Qdrant, MCP server, CSV upload in the hosted beta, auth, deployment, multi-tenancy, the kit extraction.

# Ledgerline v0.1 — plan

**Outcome:** A Python service and CLI where a natural-language question about a registered schema becomes a validated structured intent, then a parameterized SQL query on a read-only connection. An eval harness reports accuracy per schema against LangChain's SQL agent across at least 3 schemas, and everything except live evals runs with no API key.

**PRs:** one PR. Each phase only works on top of the previous one (core → pipeline → evals → UI), and v0.1 is a single shippable slice. It is built and committed phase by phase.

## Stack (fixed for this build)
- **Core:** Python 3.12 (uv), FastAPI, Pydantic v2, pydantic-settings, SQLAlchemy 2 Core, psycopg, sqlite3, LangGraph and langchain-openai pointed at OpenRouter.
- **Tooling:** Typer CLI, pytest, hypothesis, pytest-cov, ruff, pyright.
- **Web:** Next.js (TypeScript, npm) for one screen.
- **Infra:** Docker Compose (Postgres 16, api, web), GitHub Actions.
- **Baseline:** LangChain's SQL agent (`langchain-community` SQLDatabaseToolkit).
- New dependencies outside this list need a callback.

## Phases

### P1 — Foundations and gold questions (written before the intent model exists)
1. Scaffold the uv project, `ledgerline` package, Typer CLI, ruff/pyright/pytest config, a GitHub Actions workflow (lint, typecheck, tests, replay eval; no secrets) and `.env.example`.
2. Docker Compose: Postgres plus a seed job. Synthetic **fieldservice** schema (customers, sites, technicians, work_orders, parts, work_order_parts, invoices), generated by Faker with a fixed seed. About 5k work orders across 24 months. Create two roles: owner, and `ledgerline_ro` (read-only).
3. **Model gateway** (`ledgerline/llm/`):
   - `get_chat_model(tier)` returns an OpenRouter `ChatOpenAI`.
   - Structured output uses a Pydantic schema.
   - **Replay:** a JSONL store keyed by the hash of model + messages + schema. Modes: `record`, `replay`, `live`. A replay miss fails loudly.
   - A cost meter reads OpenRouter usage, falling back to token × price table.
   - A **budget guard** aborts a run before it exceeds `--budget` dollars.
4. **Gold set** `evals/gold/fieldservice.jsonl`:
   - At least 45 questions, each with `id, question, category (in_schema|out_of_schema|should_refuse), gold_sql`.
   - At least 10 must be out_of_schema and at least 8 should_refuse.
   - Commit it in this phase, before `ledgerline/intent.py` exists, so the eval is not fitted to the schema.

**Exit checks:** `docker compose up -d db seed` loads the data. `uv run pytest` passes. A gateway unit test passes in replay mode with no key. The budget-guard test passes.

### P2 — Registry, validator, SQL builder, executor (plain Python, the correctness core)
1. **Registry model** (`registry.py`, Pydantic, YAML on disk, `schema_version: 1`):
   - entities (tables or registry-declared views) with descriptions
   - fields: name, type (int|float|decimal|text|date|datetime|bool), description, aliases, filterable, aggregatable
   - relationships from foreign keys
   - allowed-value sources for categorical fields
2. **`ledgerline registry init <db-url> -o file.yaml`:** introspects with the SQLAlchemy inspector (Postgres and SQLite). Drafts entities, fields, types and foreign-key relationships, marks the file `draft: true`, and auto-detects categoricals (≤50 distinct values). `ledgerline registry values refresh` fills in the allowed values.
3. **Intent model** (`intent.py`), with these fields:
   - `intent_type`: summary | grouped_summary | row_list | unanswerable
   - `entity`
   - `metrics`: count | count_distinct | sum | avg | min | max on a field
   - `filters`: eq | in | gte | lte | between | is_null
   - `group_by`: fields plus calendar grains day/week/month/quarter/year
   - `date_range`, `order_by`, `limit`
   - `unanswerable_reason`

   Fields may be qualified as `entity.field`, reached through registry relationships (at most 2 hops).
4. **Validator** (`validate.py`) returns a list of typed errors. It rejects:
   - unknown entity or field
   - a field not reachable through declared relationships
   - an aggregate on a type that doesn't support it
   - a date range on a non-date field
   - a value outside the allowed set, after alias resolution
   - a limit above the cap (default 1000)
   - an empty select
5. **SQL builder** (`sqlbuild.py`): SQLAlchemy Core only. Identifiers come only from the registry. Every value is a bound parameter, and joins come only from declared relationships.
6. **Executor:**
   - Postgres runs on the `ledgerline_ro` role with `statement_timeout` (default 5s) and `default_transaction_read_only`.
   - SQLite opens read-only (`mode=ro` URI).
   - A row cap is applied.

**Exit checks:** named validator tests for each rejection rule. Hypothesis property: for random valid intents, no filter value appears in the compiled SQL text, and every value is in the params. Injection fixtures are bound as parameters and the DB is unchanged. A write through the executor fails on both engines. Timeout and row cap tests. Coverage ≥95% on `validate.py` and `sqlbuild.py`.

### P3 — Pipeline, API, CLI
1. **LangGraph graph:** interpret → validate → (retry once with errors) → execute → present.
   - The interpret prompt is built from a compact view of the registry: fields, types, aliases and allowed values, capped by size.
   - An `unanswerable` intent, or a second validation failure, returns a **refusal** with a reason and no SQL.
   - Prompts are versioned files under `ledgerline/prompts/`.
2. **FastAPI** `POST /ask {schema_id, question}` returns `{intent, validation: {ok, errors}, sql, params, rows, columns, refusal, trace_id, cost_usd}`. Also `GET /schemas` and `GET /healthz`.
3. **CLI:** `ledgerline ask --schema fieldservice "..."`, which prints the same trace.

**Exit checks:** API tests run in replay mode for an answerable question, an out-of-registry question (refusal, no SQL) and a retry-then-success question.

### P4 — Eval harness and benchmark
1. **`ledgerline eval --schema <id>|--all --system ledgerline|baseline|both --mode replay|live --models a,b --budget N`**
   - Scoring compares execution results (unordered, numeric tolerance 1e-6, column order ignored) against `gold_sql` results.
   - Refusal scoring: should_refuse and out_of_schema questions count as correct when the system refuses or returns the gold result.
   - Also records invalid-SQL rate, cost and latency.
2. **Baseline:** the LangChain SQL agent on the same model and the same DB (read-only), with an equal budget guard.
3. **Benchmark data** (`scripts/fetch_benchmarks.py`): downloads Spider dev and BIRD mini-dev into `data/` (gitignored), with licence notices. Deterministic subsets, filtered to questions answerable from one database:
   - **Spider:** 50 questions across 5 or more databases.
   - **BIRD:** 50 questions across 3 or more databases.

   Their registries are produced by `registry init` with **no hand edits** (this is the "your own schema" number). The fieldservice registry may be hand-curated, and the report labels which is which.
4. **Report** `evals/reports/<date>.md` plus JSON:
   - a table of schema × system × model showing execution accuracy, refusal accuracy, invalid-SQL rate, mean cost and p50 latency
   - a list of the questions where the baseline beat Ledgerline
5. **Replay recordings** for fieldservice, both systems, the default model, are committed. CI runs `eval --schema fieldservice --mode replay` and checks the numbers match the committed report.

**Exit checks:** the replay eval reproduces the report in CI with no key. A live run report exists covering at least 3 schemas and at least 2 OpenRouter models, under a $5 total budget (run by the orchestrator with Cristian's key).

### P5 — One screen, packaging, docs
1. **Next.js page:** pick a schema, ask a question, and see the trace panels: question → intent JSON → validator verdict (errors highlighted) → SQL + params → result table, or the refusal reason. The API base URL comes from env.
2. **Compose** includes api and web. A Dockerfile is provided for each.
3. **Docs:**
   - README: the problem, a mermaid architecture diagram, quickstart (`docker compose up`, `uv run ledgerline seed`), the eval table, and limits
   - `docs/product-brief.md`
   - `docs/adr/` with at least 5 ADRs: intent-not-SQL, LangGraph boundary vs plain-Python core, SQLAlchemy Core builder, replay and budget guard, benchmark methodology. Each records a prediction and the measured result.
   - `docs/build-log.md`
   - `docs/failures/` with at least 3 real eval failures (trace, cause, fix or known limit)
   - Apache-2.0 LICENSE

**Exit checks:** a Playwright smoke test (the npm `@playwright/test` dev dependency in web/) against the replay API shows all trace panels for one question. `docker compose up` serves the web UI and the API.

## Acceptance criteria
- **L1** `uv run ruff check`, `uv run pyright` and `uv run pytest` all pass. The CI workflow runs them plus the replay eval with no secrets.
- **L2** Coverage is ≥95% on `validate.py` and `sqlbuild.py`, enforced by pytest-cov `--cov-fail-under` on those modules.
- **L3** The validator has one named passing test per rejection rule in P2.4.
- **L4** The Hypothesis property test passes, and the injection fixtures leave the DB unchanged, with every value bound as a parameter.
- **L5** Executor writes fail on Postgres (read-only role) and SQLite (mode=ro). Timeout and row cap are enforced (tests).
- **L6** `registry init` on fieldservice Postgres and on one Spider SQLite DB produces YAML that loads in the registry model and includes foreign-key relationships (test).
- **L7** `POST /ask` returns the full trace. An out-of-registry question returns a refusal with `sql: null` (replay test).
- **L8** The fieldservice gold set has ≥45 questions, ≥10 out_of_schema and ≥8 should_refuse. It was committed before `intent.py` first appears, which `git log` can show.
- **L9** The replay eval in CI reproduces the committed fieldservice report numbers.
- **L10** A committed live report covers ≥3 schemas (fieldservice; Spider ≥50 questions across ≥5 DBs; BIRD ≥50 questions across ≥3 DBs), Ledgerline vs the baseline, on ≥2 models. It lists the questions where the baseline won, and the total spend is ≤$5.
- **L11** The budget guard aborts before the cap is exceeded (test with a fake cost meter). A replay miss raises an error.
- **L12** No Spider or BIRD data is committed. `scripts/fetch_benchmarks.py` exists with licence notices.
- **L13** The Playwright smoke test passes against replay.
- **L14** The docs set in P5.3 exists, and every ADR has a prediction and a measured result.
- **L15** `docker compose up` serves the API and web, and both Dockerfiles build.
- **L16** No secrets are in the repo: a gitleaks or `detect-secrets` scan runs in CI, and only `.env.example` is committed.
